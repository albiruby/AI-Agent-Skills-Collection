# Example: CLI, API, or Library

## 1. Request

> Document this CLI and produce a GitHub social card plus a README example. Do not expose tokens or personal paths.

## 2. Context

- Commands, flags, exit codes, config, installation.
- API/SDK contracts, errors, limits.
- Architecture and key flows.
- Existing docs and brand assets.

## 3. Visual options

For developer tools, screenshots are often less useful than:

- Clean terminal renders with real commands/output.
- Request/response cards.
- Mermaid architecture/sequence diagrams.
- Code examples with syntax highlighting.

Do not fabricate terminal output. If output is illustrative, label it as an example.

## 4. Capture terminal

- Use a clean theme with sufficient contrast.
- Hide personal paths, hostnames, tokens, shell history, and customer data.
- Show the smallest command that demonstrates value.
- Keep output readable; truncate long output intentionally.
- Prefer vector/text assets where the destination supports them.

## 5. Compose social/preview

- GitHub 1280x640 or OG 1200x630.
- Terminal card or architecture diagram as the focal point.
- One-line value proposition, no hype.
- Consistent palette with the docs.

## 6. Documentation

- README: install, one best example, commands, docs links.
- CLI reference: commands, flags, defaults, examples, exit codes.
- API reference: auth, endpoints, types, errors, limits.
- Architecture: modules, data flow, persistence, external calls.
- Changelog and migration notes.

## 7. QA

- Every command exists and runs.
- No secrets, private URLs, or personal paths.
- Diagrams render.
- Social/OG dimensions correct.
- Claims match runtime behavior.
- Limitations and unsupported platforms stated.

## 8. Handoff

Include docs, diagrams, clean visuals, manifest, QA report, and unverified items.
